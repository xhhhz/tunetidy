# 理音 TuneTidy · 架构说明

写给想读懂或修改理音代码的人。使用方法见 [README](../README.md)。

## 整体流程

```
读取歌单与曲风标签 ──► 分类 ──► 整理方案（本地） ──► 人工确认 ──► 写回账号 ──► 可撤销
   analyze.py          classify/     plan.py            apply/approval   apply/writer   apply/undo
```

1. **读取**：通过后端接口拉取来源歌单的歌曲和每首歌的官方曲风标签。标签逐首写进本地数据库，中断后再运行会接着取，并按配置缓存一段时间。
2. **分类**：只用本地数据完成，不访问网络。同一份输入一定得到同一份结果。
3. **整理方案**：分类结果、将要新建的歌单、以及当时用到的全部输入（信号快照）一起存进数据库。之后切换拆法、移动歌曲、改歌单名，都基于这份快照重新计算，不再访问网络。
4. **确认**：只能由人在交互式终端里输入确认码完成。确认时记下方案内容的哈希。
5. **写回**：执行前重新核对哈希；先把"要建哪些歌单、各加哪些歌"写进数据库，再逐步执行，中断后可以续传。
6. **撤销**：先回读歌单现状、和写入记录对比，再决定整删还是只移除理音加入的歌。

命令行、网页和 MCP 服务是同一套核心库的三个入口。

## 目录

| 位置 | 作用 |
| --- | --- |
| `src/tunetidy/models.py` | 平台无关的数据类型（歌曲、歌单、标签等），歌曲主键一律是 `(platform, id)` |
| `src/tunetidy/backends/` | 访问音乐平台的唯一位置。`base.py` 定义 `MusicBackend` 接口，`web/` 是网易云扫码登录后端 |
| `src/tunetidy/signals/` | 把平台数据转成分类用的信号（目前是官方曲风标签） |
| `src/tunetidy/classify/` | 曲风树、多标签规则、打分、拆分方式、小类合并 |
| `src/tunetidy/analyze.py` | 串起读取、分类、生成方案；按快照重新分类、移动歌曲、改歌单名 |
| `src/tunetidy/plan.py` | 方案、将要新建的歌单、内容哈希 |
| `src/tunetidy/apply/` | 确认、写回、续传、撤销 |
| `src/tunetidy/storage/` | SQLite 读写（WAL 模式）、表结构迁移 |
| `src/tunetidy/jobs.py` | 后台任务（分析、写回），供 MCP 使用 |
| `src/tunetidy/server/` | 本地网页服务（FastAPI）和接口 |
| `src/tunetidy/mcp/` | MCP 服务：五个工具的逻辑和注册 |
| `src/tunetidy/cli.py` | 命令行入口（Typer + Rich） |
| `web/` | 网页前端（React + TypeScript + Vite + Tailwind），构建产物打进 Python 包 |
| `taxonomies/` | 网易云曲风树快照与自定义分组示例 |
| `scripts/` | 评估脚本、本地 pre-commit 钩子 |

## 关键设计

### 平台隔离

上层模块只依赖 `MusicBackend` 接口，不直接发请求。后端按名字注册，用到时才导入，所以删掉 `backends/web/` 整个目录，其他模块仍能编译、测试仍能运行。以后接入其他平台，只需新增一个后端。

### 确定性分类

1. 每首歌的官方标签先按曲风树归到大类，再去掉用途类标签（原声带、二次元、儿童）和泛化标签（流行），前提是还剩别的曲风。
2. 剩下的曲风按当前拆法映射到分类：按大类、按细类、只分一类、自定义分组。
3. 只对应一个分类就放进去；对应多个分类、分不出主次，或者没有标签，就标为"没分好"，不写入。
4. 再按设置把太小的分类并入「其他」、只保留最大的 N 类，或者不建「其他」。

结果与歌曲顺序无关，同一份快照必然得到同一份方案。人工调整（移动歌曲）单独标记，重新分类时保留。

### 方案状态与确认

状态依次为：草稿 → 已确认 → 正在创建 → 已建好 → 已撤销。

- 内容哈希只覆盖"会对账号做什么"：来源、每个新歌单的名称和歌曲顺序、不写入的歌。确认后内容有任何变化，确认自动作废，方案回到草稿。
- `approve`，以及命令行里的 `apply`（不论带不带 `--yes`），都只在交互式终端下工作，并要求输入随机确认码。
- 非交互地执行已确认的方案，只有 MCP 的 `apply_plan` 一条路径；它同样核对状态和哈希，没有确认工具。
- 已建好的方案不能再执行一次。

### 写回与撤销

- 写回前先在 `runs`、`run_playlists`、`run_tracks` 三张表里记下意图，再建歌单、分批加歌。每个新歌单的简介里写入运行标记。
- 中断后续传：按记录跳过已完成的部分，按运行标记找回已建的歌单，不会建出第二个。
- 只新建歌单，从不修改或删除用户原有的歌单。
- 撤销前回读歌单现状：和写入记录完全一致才整删；用户改过（或找不到运行标记）的，只移除理音加入的歌。

### 存储与并发

SQLite 开启 WAL 模式；命令行、网页服务、MCP 服务可能同时打开同一个库。写操作都是短事务（`BEGIN IMMEDIATE`），表结构变化通过只追加的迁移完成。

后台任务记在 `jobs` 表里：

- 同一时间只允许一个在运行，检查和插入在同一个写事务里完成，跨进程也成立；
- 运行中每 10 秒刷新心跳；
- 任何入口启动时，把进程已不在或心跳超时的任务标为"已中断"。

### 本地网页服务

- 只监听 `127.0.0.1`；
- 每次启动生成随机口令，放在网址的 `#token=` 里（不会发给服务器、不进日志）；
- 每个接口请求都要带口令请求头，并校验 `Host` 和 `Origin`；
- 写接口只接受 POST；
- 网页只能查看和修改本地方案，不能确认、写回或撤销。

### MCP 服务

`tunetidy mcp` 以 stdio 启动，五个工具：`list_playlists`、`create_plan`、`get_job_status`、`get_plan_items`、`apply_plan`。

- 分析和写回都只启动后台任务、立即返回任务 id。
- 默认只返回摘要，明细分页。
- 参数里没有限速、间隔、并发之类的设置。
- stdout 只输出协议消息。

### 凭据与隐私

- 登录态优先存系统钥匙串，不可用时存仅本人可读的文件；日志和报错不打印凭据。
- 访问平台时按配置限速，并带随机间隔。
- `scripts/hooks/` 提供一个本地 pre-commit 钩子：从本机数据库和钥匙串读出自己的歌单 id、用户 id、昵称和 Cookie，暂存内容命中就拒绝提交。启用方法：`git config core.hooksPath scripts/hooks`。

## 测试

- `uv run pytest` 全部离线：平台响应来自 `tests/fixtures/` 里脱敏后的录制数据，后端用 `tests/fakes.py` 的假实现，钥匙串在测试里被强制换成内存实现。
- 真实接口测试在 `tests/live/`，标记为 `live`，默认不运行。
- 写回、续传、撤销、确认失效、后台任务中断等边界情况都有测试。
